# TVBoxOS → HarmonyOS 7（Mate 80）移植报告

> 分析基准：`q215613905/TVBoxOS` 的 `main` 分支，提交 `89ec1b7504426b3ff5e9d0996c3bbf50c9d2eff0`（2026-11-11）。源码通过 GitHub API / raw 文件读取分析；本会话中完整 `git clone` 超时，未做全量本地代码审阅，因此本报告是**基于目录树、构建脚本、Manifest 与关键类的路线评估**，不是逐文件迁移清单。

## 1. 结论（一句话）

**这不是 APK 重打包，而是一次 ArkTS + ArkUI 原生重写**：保留 TVBox 的配置格式、数据模型与 Spider 接口契约，重写 UI、平台能力调用、爬虫运行时和播放器；Java JAR / Python 爬虫运行时是最大的不可直接迁移部分。

目标设备：Mate 80；目标系统：HarmonyOS 7（公开资料显示对应 SDK/API 26.x，Mate 80 已在推送范围内）。HarmonyOS 7 为纯鸿蒙体系，不运行 Android APK/DEX，因此上述结论成立。

## 3. 选路决策

| 源能力 | 鸿蒙方案 | 决策 |
|---|---|---|
| 78 个 XML 布局 + Activity/Fragment/Dialog | ArkUI声明式组件 + UIAbility + `router`/`Navigation` | 全部重写。Mate 80 是手机，保留横屏体验，但不照搬 Leanback/TV 遥控器逻辑为第一优先级 |
| JSON 配置 / 数据模型 / 收藏历史 | ArkTS 数据类 + `JSON.parse`；`preferences`（设置/配置地址）与 `relationalStore`（历史/收藏/缓存） | 可复用结构与业务规则 |
| OkHttp/Cronet/Gson/jsoup/XStream | `@kit.NetworkKit`（`http`/`rcp`）；JSON 用原生解析；XML/HTML 解析评估 ohpm 包或 NAPI 复用 | 网络层重写，Cronet 依赖丢弃 |
| **JAR Spider（DexClassLoader）** | 鸿蒙不能加载 DEX/JAR | **核心阻塞项**。三条出路：①用 ArkWeb 的 JS 运行时承载 `cat.js` 类脚本 + JavaScriptProxy 注入 JSAPI；②把爬虫放到服务端，端侧只调 HTTP API；③将 JAR 逻辑人工转写为 ArkTS。建议 ①+②并行：JS 源优先，JAR 源走服务端代理 |
| **Python Spider（pyramid/Chaquopy）** | 鸿蒙无法运行 CPython + pip 包 | 只能服务端化或逐个用 ArkTS/JS 重写；lxml、pyquery、加密协议是主要工作量 |
| IJKPlayer / ExoPlayer（player 模块） | 先用 `media.AVPlayer`（`@kit.MediaKit`）+ XComponent/Video；不兼容的协议再评估 NAPI 封装 ffmpeg/ijk 的 `.so` | 分两级：系统播放器优先，NAPI 兜底；不要一上来移植 native 播放器 |
| DLNA 投屏（Cling + nanohttpd） | 系统投播/扩展屏投播能力（API 名称与可用范围需在 DevEco 26 SDK 中逐项查证） | 原 Java 协议栈不可用；一期可降级为“系统分享/投屏”，二期再接系统投播 |
| 弹幕/字幕 | 字幕：`AVPlayer` 外挂字幕回调 + 自绘；弹幕：ArkUI 自绘或 NAPI 复用渲染库 | DanmakuFlameMaster 需重做 |
| 远程控制本地 HTTP（nanohttpd） | `@kit.NetworkKit` socket 服务端（具体接口待验证）或去掉 | 一期砍掉 |
| 权限 | 仅声明 `ohos.permission.INTERNET` 等实际用到的权限；存储改用应用沙箱 + CoreFileKit | 删除安装 APK、定位、无线多播等无关权限 |

## 4. 分阶段实施

1. **阶段 0｜边界冻结（0.5 天）**
   固定源提交 `89ec1b7`；确认只做手机（Mate 80 / HarmonyOS 7 / API 26.x）；确认最低兼容版本；确认 AGPL 合规策略；挑选 1～3 个真实配置源作为验收样本。
2. **阶段 1｜可运行骨架（1～2 周）**
   Stage 工程、EntryAbility、首页、配置地址导入与持久化、网络层、JSON 数据模型。验收：Mate 80 真机安装 HAP，导入配置 URL 能拉取 `sites` 列表并显示。
3. **阶段 2｜Spider 契约与 JS 运行时（2～4 周）**
   ArkTS `SpiderContract` 对齐 `Spider.java` 全部方法；用 ArkWeb 注入 JSAPI（网络、存储、日志、加解密）跑通 `cat.js` 模板；实现 1 个真实 JS 源的 首页→分类→搜索→详情→播放列表全链路。验收：与 Android 版同字段输出对比一致。
4. **阶段 3｜播放器（2～4 周）**
   `AVPlayer` 播放直链/m3u8、Header/UA/Referer、倍速、跳转、续播、外挂字幕、弹幕叠加、播放失败切换线路；直播 EPG。验收：1 个 VOD 源 + 1 个直播源可播、可拖、可恢复。
5. **阶段 4｜完整功能（3～6 周）**
   多仓切换、收藏/历史、设置、搜索历史、快速搜索、壁纸、画中画、投屏、横屏布局与折叠屏适配；远程控制视优先级决定恢复或砍掉。
6. **阶段 5｜质量与交付（1～2 周）**
   真机性能（列表滚动、首帧时间、内存）、权限拒绝分支、弱网与源失效分支、hilog 无未处理异常；DevEco 自动签名调试，AGC 签名发布。

**工作量判断**：阶段 1 可较快完成；阶段 2 和 3 决定项目成败；完整等价替换原项目 966 次提交积累的功能，属于**多人月级别**工程，不建议承诺“一次移植等价”。

## 5. 风险与未决问题

- **JAR/Python 爬虫不可直接复用**：这是全局最高风险。需要在阶段 2 用真实源验证 JS 方案覆盖率；覆盖率不足则只能依赖服务端代理。
- **配置源兼容性**：字段、扩展参数、加密协议随源而异；`ApiConfig.java` 有大量兼容逻辑（AES、正则、M3u8、代理、DNS、Hosts），需逐项迁移。
- **播放器协议**：源站返回重定向、鉴权、私有加密时，AVPlayer 可能不支持；NAPI 方案需评估维护成本与 so 的架构兼容。
- **投屏**：Cling/nanohttpd 是 Java 栈，系统投播 API 的能力边界必须查证后再承诺。
- **合规/许可证**：AGPL v3 的衍生作品与网络服务义务；第三方配置源/爬虫的版权与内容合规风险由使用者自行确认。
- **未验证项**：本会话未编译、未安装到 Mate 80；工程配置文件中的 SDK 版本号需以本机 DevEco Studio 26 模板为准调整。
